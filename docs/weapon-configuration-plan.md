# CM2 武器配置系统改造计划

## 适用范围

本计划只适用于：

- `Content Mod 2/script/`
- 神秘战列巡洋舰脚本
- 新武器配置系统及其 UI

本阶段不处理：

- `Global Mod/`
- `script_titan/`
- `script_riddle_escort/`

## 总体目标

将飞船框架与具体武器配置分离，使玩家可以在客户端 UI 中为每个武器组统一选择一种武器。

保留当前战列巡洋舰的职责划分：

1. 飞船决定可用的武器框架。
2. 飞船决定武器的装载数量、位置、方向和瞄准方式。
3. 飞船决定各武器组的操作方式、开火顺序和开火逻辑。
4. 飞船通过武器池限制每个武器组允许安装的武器。
5. 武器提供伤害、射程、弹丸、光束和特效等具体行为与参数。
6. 玩家只在飞船允许的范围内，为整个武器组选择一种武器。

遵守两个结构原则：

1. 船体系统与武器系统分离。
2. 运行脚本与纯配置数据分离。

状态：已完成。

脚本：

- `check-encoding.ps1`

- 可能的 ANSI/GBK 编码

脚本：

- `check-lua.ps1`
- `test-check-lua.ps1`

检查内容：

- Lua 语法错误
- 缺失的 `#include`
- 格式错误的 `#include`
- 越出检查根目录的 include
- 循环 include 调用链
- Teardown 内置 `script/include/...` 特殊引用

## 第三阶段：拆分 M/G 武器组开火架构

状态：代码改造已完成，等待 Teardown 实机验证。

### 目标

取消旧代码中把 M 槽和 G 槽混合为 `sSlot` 的实现，使两种槽位拥有独立的模式、请求、冷却、调度和 HUD 状态，同时复用与槽位无关的制导弹丸运行逻辑。

职责划分：

1. 飞船侧的 fire control 负责 M/G 武器组、装载点、轮流开火和输入调度。
2. 武器运行时负责弹丸生成、制导移动、碰撞与伤害。
3. 当前 M 槽蜂群导弹与 G 槽毁灭者鱼雷可以复用通用制导弹丸运行时，但不会因此合并为同一个武器组。
4. M/G 各自维护开火请求、发射器序号和冷却状态，切换武器组不会串用状态。
5. 当前两种武器都继续使用目标锁定；以后新增非制导武器时，再由武器定义提供不同的开火方式。

### 完成条件

- 主武器模式能够独立识别 `mSlot` 和 `gSlot`。
- 不包含 G 槽的框架切换武器时会跳过 G 槽。
- M/G 请求不会进入对方的控制器。
- M/G HUD 分别显示自己的冷却状态。
- Lua 语法、include 调用链和编码检查全部通过。
- 在 Teardown 中分别验证 battleline 与 siege 框架的切换、锁定、开火和命中。

## 第四阶段：武器配置 UI MVP

状态：第三阶段实机验证后执行。

### 目标

编写一个与当前战斗系统隔离的客户端 UI 模块。先验证 Teardown UI API 的可靠性、稳定性和可行性，再验证玩家能否为每个武器组统一选择武器。

第一版流程：

```text
打开武器配置 UI
        ↓
验证界面显示、按钮点击和打开/关闭
        ↓
在客户端内存中切换测试选项
        ↓
确认 UI 不干扰飞船开火与镜头操作
```

UI API 验证通过后的数据流程：

```text
读取战巡武器框架
        ↓
显示框架中的武器组
        ↓
读取对应武器组允许使用的武器池
        ↓
玩家为整个武器组选择一种武器
        ↓
在客户端内存中生成 loadout
```

### MVP 必须完成

1. 使用硬编码测试数据验证 Teardown UI 的显示、交互、状态保持和分辨率适配。
2. 验证配置 UI 打开时不会误触发飞船开火、镜头或其他操作。
3. 从飞船数据中读取可用的武器框架。
4. 从框架的 `slotGroups` 中读取武器组，不拆分成 `X1`、`X2`、`L1`、`L2` 等单独炮位。
5. 从飞船的 `slotWeaponPools` 中读取各武器组允许安装的武器。
6. 从武器数据中读取武器类型和基础展示信息。
7. 支持玩家为整个武器组统一选择一种武器。
8. 将选择结果保存在客户端 Lua 内存中。
9. 能够在 UI 中查看当前生成的完整 loadout，例如 `loadout.X`、`loadout.L`、`loadout.M`、`loadout.G` 和 `loadout.H`。

### MVP 暂不实现

- 不写入 Registry。
- 不修改当前服务端武器状态机。
- 不实际替换战斗中的武器。
- 不进行反作弊或复杂权限验证。
- 不实现配置持久化。
- 不同步给其他客户端。

### 隔离要求

新 UI 代码应放在：

```text
Content Mod 2/script/weapon/client/config_ui/
```

在 MVP 验证完成前，新模块不应直接修改现有武器控制器、伤害代码或服务端 loadout。

现有服务端 loadout 按武器组保存配置的结构保持不变；本阶段不改造成单个炮位独立配置。

## 第五阶段：服务端接入

状态：第四阶段完成后执行。

计划流程：

```text
客户端完成配置
        ↓
玩家点击应用
        ↓ ServerCall
发送完整 loadout
        ↓
服务端保存到当前飞船的 Lua 内存
        ↓
服务端按照新配置重建武器运行状态
```

原则：

- 客户端负责决定配置。
- 服务端负责接收并执行配置。
- 不使用 Registry 保存完整武器配置。
- 服务端只做防止脚本报错所需的最低限度检查。
- 配置只在初始化或玩家应用更改时同步，不进行每帧同步。

## 每阶段完成条件

每次修改完成后必须运行：

```powershell
.\check-encoding.ps1 -Path ".\Content Mod 2\script"
.\check-lua.ps1 -Path ".\Content Mod 2\script"
.\test-check-encoding.ps1
.\test-check-lua.ps1
```

涉及运行逻辑、生命周期或 include 路径变化时，还必须进入 Teardown 进行实机验证。
